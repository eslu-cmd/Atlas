# Step 4B relationships and storage boundary

Records implementation 0.2.1 supersedes 0.2.0 with the three bounded fixes in `Repair-0.2.1-Notes.md`. The storage schema remains version 1; no data migration is required.

All business records are immutable snapshots. Changes append records with predecessor links and, through the change operations, explicit H01–H10 events. Every record has its own ID, kind, actor, reason, recorded UTC time, optional effective time, and source/illustrative/operational provenance. Effective time is left absent unless supplied. Provenance is attribution, not verification.

## Identity and reference model

| Record kinds | Identity, owned context and retrieval |
|---|---|
| dictionary, specification | Store the entire issuing dictionary document and its digest. Store the entire canonical A1 code with its dictionary reference. Exact repeated codes reuse one specification. Incompatible later dictionary meanings are rejected. No product lookup replaces decoding. |
| supplier, product, sku, version | Product reference and optional original SKU are supplier scoped. Additional SKU records retain previous SKU references. Physical versions belong permanently to one product and can link a predecessor. Neither close measurements nor equal codes merge these identities. |
| association | A version's link to a specification. Clarification and correction retain the version and append a new association, with original wording remaining in assertions. `current_association` follows the explicit revision chain and excludes withdrawn associations. Historical contexts retain old association IDs. |
| source, location, assertion, finding, attachment | Sources preserve URI, optional hash and metadata. Locations preserve precise cells/pages/messages. Assertions retain literal statements, supplied values, interpretation and uncertainty state. Findings append subsequent conclusions without erasing claims. Attachments retain URI, media type and optional hash/caption. No universal verification field exists. |
| triage | Original source snapshot, precise location, assertions and optional encoded description. Encoding does not resolve product identity. Both encoded and unencoded descriptions can have unresolved identity. |
| client, request, job | Requirements, usage, distribution, source/attachment links and unresolved qualifications remain separate from supplier facts. Known client/request/job links must agree. Missing client/job values are not manufactured. |
| customization | A revision belongs to exactly one physical version or kit revision, with client/request/job context where supplied. Printing details remain a literal structured object; artwork and proofs are attachment references. A revision cannot move to another physical/client/job context. There is no required printability field. |
| kit, kit_revision, component | Kit is supplier scoped. Each revision links an ordered list of immutable membership records. Each component references a specification association, thereby preserving its version, product and supplier. Quantities use supplied value/unit or null plus an explicit state. Separate saleability is explicit and never inferred. Opening a component version can retrieve every historical membership. No combined kit Spec ID exists. |
| packing | Supplied packing facts belong to a version or kit revision. Alternatives/revisions do not mutate specifications. |
| context | Immutable exact scope: either version + association, or kit revision; optional customization, packing, client, request and job. Cross-version customization/packing and inconsistent client/job links fail. Kit specifications are reached through its revision's components. |
| quote | Supplied prices, currency, bases, breaks, validity, tooling, Incoterms and dates remain supplied values in an object, with evidence and explicit discrepancies where known. It points to one immutable context; new packing/commercial terms never rewrite old quotes. No arithmetic is recalculated. |
| sequence, sample, sample_note | Sequence belongs to exactly one permanent supplier product or supplier kit, with known client/request/job scope. A product sample pins a physical version/association; a kit sample pins a kit revision and its composition. V1/V2 labels are unique only inside that sequence. Each sample references its exact context; physical or kit-composition change requires separate revision creation. V2 alone creates neither. Component approvals do not establish assembled-kit approval, and changed compositions do not inherit approvals. Notes retain photos, comments, requests and evidence without rewriting earlier iterations. |
| approval | Separate `proof_agreement`, `source_one_acceptance`, `client_approval`. Required evidence, actor and decision retain scope. Proof agreement requires customization; sample acceptance requires a sample; client approval requires a client. A linked sample must have the same exact physical/kit, association, customization and packing references and the same resolved business scope. Redundant client/request links implied by a job are equivalent. Different jobs/requests/clients and missing-versus-known scope remain distinct. Contradictory explicit and inherited scope is rejected. No evidence is inherited from a specification. |
| compatibility | Supplier claim versus human confirmation, exact pair of physical versions, conditions, evidence and person/date when known. Human confirmation requires the confirmer's identity. Shared dimensions/codes and later versions inherit none. |
| capability | Supplier-linked alternatives and conditions. It cannot be used as a version, quote, sample or approval target. No joint feasibility is inferred between alternatives. |
| handoff | Immutable agreed context, quote, approvals, attachments and qualifications. Linked quote/approvals must agree with the handoff context. Withdrawn approval cannot support a newly created handoff. Existing handoffs retain original references plus later corrections. |
| event | H01–H10 history with old/new references, evidence and recorded metadata. H08 explains identity resolution with explicit identity evidence; it does not move histories or collapse keys. |

Uncertainty states are `not_supplied`, `explicitly_unknown`, `not_applicable`, `ambiguous`, `conflicting`, `unsupported`, and `stated`. `stated` means an assertion was supplied, not independently validated. Preserve competing statements as separate assertions; do not turn them into a resolved association without review. Raw source values, formulas and caches remain literal supplied content.

## Change and correction behavior

- H01/H06: `change_association` validates the current predecessor, appends a new association and event, and preserves all earlier context. H06 withdraws the incorrect current indication. H06 can also be recorded without a replacement to withhold an unsupported association.
- H02: `revise` creates a linked physical version. Create its new association in the same outer transaction. No new version or description is inferred from sampling alone.
- H03/H04/H05: `revise` creates customization, packing or quotation snapshots. Commercial revisions keep the same physical/kit target and client/job scope. A quotation for a new physical or kit revision is a new quote with its own context.
- H07: `correct_approval` withdraws a wrong approval association; an explicit supported destination creates a new approval retaining the original approval evidence. The H07 event separately references evidence supporting reassociation. Opening the replacement or a handoff referencing it exposes incoming H07 events and predecessor records in `correction_provenance`. This separate structure contains `events`, the expanded `records` (including approval documents, sources, assertions and correction notes), and `approval_status` mapping approval IDs to active/withdrawn booleans. Former contexts remain historical and are not inserted into the current `original_context`. Successive explicit corrections remain linked through their H07 events. Without a destination, the event remains unresolved. The original evidence and actor/context are not overwritten.
- H08: `resolve_identity` requires an assertion marked `evidence_kind: identity`; the human-provided evidence must concern actual offering identity. Equal codes are insufficient. The operation records old/new references and explanation, retaining both identities and their histories. Destructive merge and automated rehoming are deliberately absent.
- H09/H10: `revise` appends sample iterations or kit composition revisions. Earlier photos, decisions and kit membership stay on their original records.

`history(id)` traverses the original outgoing graph, including dictionaries and exact specification associations. It leaves `previous` as a lineage link rather than splicing predecessor content into the snapshot. Separately, it returns later correction events/findings and later predecessor-linked revisions, following successive corrections. “Later” is relative to the affected record; corrections remain visible even when an old quote is entered retrospectively after a correction. Corrections are associated through affected records; shared specification/source/dictionary/client nodes do not spread another supplier's corrections. `is_active` describes direct withdrawal only; it is not a product-truth or approval badge. A handoff containing subsequently withdrawn evidence remains a historical handoff with a clearly labelled correction, not a newly approved handoff.

`same_context` resolves client and request from job/request links and compares that scope together with exact physical/kit, association, customization and packing links. It does not use missing information as a wildcard.

`product_history` returns only records reached through that product's versions and sequences. `sampling_history` expands product or kit iterations, notes, evidence and decisions. Retrieve a kit's sequences with `referring(kit_id, "kit", "sequence")`; no product identity or combined Spec ID is created for a kit. `memberships` reverses component associations to kit revisions. For other reverse relationships, use `referring` in the Python API. There is no general search UI or arbitrary natural-language query layer.

## Executed storage schema

The local schema has three relational tables:

1. `records(id, kind, data, actor, recorded_at, reason, effective_at, provenance)` holds typed immutable snapshots. JSON carries supplied details and dictionary documents, not hidden relationship IDs.
2. `links(owner, role, position, target)` holds ordered, foreign-key-backed relationships. Every relationship is explicit and queryable in either direction. `(owner, role, position)` is unique.
3. `unique_keys(namespace, value, record)` enforces release identity, full Spec ID uniqueness, supplier references/SKUs, initial/successor version and association lineage, and sample labels per sequence.

The `CONTRACTS` registry in `atlas/records.py` is the logical schema: required/optional data, allowed edge kinds and cardinalities. `_validate` enforces cross-record scope. This compact node/edge substrate avoids many nullable columns while preserving separate record types and relational references. Payload structures for supplied business terms are deliberately open; full intake validation is a later stage.

SQLite foreign keys are enabled on every `Store` connection. SQL triggers block updates/deletes of snapshots, links and identity keys. Savepoints make multi-record operations atomic, including nested operations; unique keys reject duplicate identifiers/lineage. Typed links, cardinality, canonical codes and semantic scope are enforced by `Store`, **not by the bare SQL tables alone**. Direct SQL inserts are not a supported application write surface. Do not expose this local schema directly to untrusted clients. Shared edit conflict handling has not been validated.

## Relation to Supabase/Postgres, Vercel and GitHub

No `package.json`, Supabase config, Vercel config or Git repository config was found in the supplied source tree during targeted setup inspection. This package adds a dependency-free local harness around the already established Python engine. It does not replace the approved hosting/database direction.

`schema/postgres-candidate.sql` translates the three storage tables to Postgres `jsonb`/`timestamptz`, indexes, foreign keys and immutable-row triggers. It has **not been executed or validated against Postgres or Supabase**. Before adoption, implement a trusted transaction adapter/service enforcing the same contracts, settle direct-write privileges and shared-edit checks, and rerun these scenarios on the actual database. Keep canonical uniqueness key serialization stable across adapters. Verify SQL/JSON behavior and migration rollback in a trial database. No production migration, role policy, Supabase Storage integration or Vercel deployment is included. GitHub can hold this package and run `python3 run_all_tests.py` in future CI; no repository or CI configuration was changed remotely.

Attachment references preserve evidence locations; this milestone does not ingest their bytes, certify remote availability or restore attachments. The source workbook remains at its original read-only location; the selected extracted batch is bundled for offline reproduction. Illustrative photo/artwork URIs intentionally reference no real image. Closing/reopening SQLite and transactional rollback are tested, but neither is the approved recovery trial.
